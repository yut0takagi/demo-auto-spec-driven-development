## ダッシュボードの見方

ダッシュボードは上部ナビ（概要 / Ideation / ゲート・離脱 / Revise / モデル比較）で
5ページに分かれています。トップページ (`src/app/page.tsx`, 概要) には稼働ステータス・
主要トレンドなど全体像を、それ以外は `src/app/{ideation,gate,revise,model}/page.tsx`
にテーマ別のパネルをまとめています。各グラフ・パネルの意味は以下の通りです（掲載順は
それぞれの表示ページ内での並び順）。

- **直近の反復サマリー**: 最新反復の判定 (verdict) を吹き出し形式で表示したもの。merged/abandoned/needs-human/paused/dry-run/failed で見出し・色分けが切り替わり、Adversary のレビューコメント（またはゲート不通過理由）を本文に表示する。
- **Adversary承認コメントの要約・トレンド**: verify到達済み反復の Adversary レビューコメント(adversary.summary)の文字数推移を折れ線で示し、直近3反復と直前3反復の平均文字数を比較して「長文化傾向」「短文化傾向」「横ばい」を判定する（変化率が±10%未満は横ばい扱い）。あわせて承認時/却下時それぞれの平均文字数と、直近5反復分のコメント本文をそのまま読めるダイジェスト一覧を表示する。failed（クラッシュ）反復のコメントは「レビューに到達しなかった」等の定型文で実際のレビューではないため対象から除く。
- **高revise + 低承認率の前兆検知**: 直近3反復（verify到達済み）の平均revise回数と承認率をローリング集計し、平均revise回数が2回を超え、かつ承認率が50%未満のときに「警戒」、どちらか一方だけ該当するときに「注視」を表示する。サーキットブレーカのように非マージが連続してから発火する事後指標とは異なり、builderが迷走し始めている段階の前兆を捉えるためのもの。
- **CI/ゲート通過時間のトレンド観測**: 各反復の所要時間(durationSec)を分単位の折れ線で表示し、直近3反復の平均と直前3反復の平均を比較して「悪化傾向」「改善傾向」「横ばい」を判定する（変化率が±5%未満は横ばい扱い）。verdict に関係なく全反復（failed も含む）が対象。反復が1件しか無い場合は比較対象が無いため傾向判定を表示しない。
- **Issue開始から初PR作成までの時間トレンド観測**: 実際にPRが作られた反復（prNumber が null でない）に限定して所要時間(durationSec)を分単位の折れ線で表示し、直近3反復の平均と直前3反復の平均を比較して「悪化傾向」「改善傾向」「横ばい」を判定する（変化率が±5%未満は横ばい扱い）。「CI/ゲート通過時間のトレンド観測」が全反復（PRを開けなかった failed/abandoned 含む）を対象にするのに対し、こちらは PR に到達した反復だけを比較することで、issue着手から最初の成果物(PR)が出るまでの速さの傾向を見る。PRが作られた反復が1件以下の場合は比較対象が無いため傾向判定を表示しない。
- **Builder稼働率低下検知（反復開始→PR作成のリードタイム逆転）**: 「Issue開始から初PR作成までの時間トレンド観測」と同じ母集団（PRが実際に作られた反復）を iteration 昇順の隣接ペアで比較し、直後の反復のほうが所要時間(durationSec)が5%以上悪化している箇所を「逆転」として抽出する。窓平均同士の比較では相殺されてしまう単発の局所的な悪化も漏らさず検出できる。データ終端に向けて2回以上連続で逆転が続いている場合のみ「発報」とし、直近の1回だけの逆転はノイズとして未発報のまま扱う（トレイリング判定のため、過去に連続逆転があっても直近が改善すればstreakは0に戻る）。逆転総数・比較ペア総数・逆転率(%)もあわせて表示する。PRが作られた反復が1件以下の場合は比較対象が無いため「データなし」。
- **Issue生成からIssueクローズまでの解決時間トレンド**: issue番号が最初にどこかの反復の nextIssues に現れた時点（生成）から、その issue が merged/abandoned のいずれかに達した反復（クローズ）までの所要時間を分単位の折れ線で表示し、直近3件の平均と直前3件の平均を比較して「悪化傾向」「改善傾向」「横ばい」を判定する（変化率が±5%未満は横ばい扱い）。同一issue番号が複数回dispatchされている場合は生成後最初のクローズだけを1件として数える。生成元が特定できないissue（seed issue等）や解決済みissueが1件以下の場合は対象外・傾向判定なしとなる。
- **Issueラベル別 成功率**: issue に付与された GitHub label 別に、その label を持つ issue を扱った反復が develop へマージされた割合(成功率)を集計し、成功率の高いラベルから一覧表示する。1つの issue が複数 label を持つ場合は該当する全ラベルのバケットに数える。例外で issue を特定できず label が空配列の反復（`data/runs/0018.json` 等）はどのバケットにも数えない。label が付いた反復が1件も無い場合は「データなし」。
- **Issue課題型別 提案品質・回収効率マトリクス**: 上記と同じ issue label（課題型）単位で、「提案品質」(Adversary が approve した割合。verify に到達した反復が無ければ測定不可)と「回収効率」(mergedCount/count、および merge 1件あたりの平均コスト。マージ実績が無ければ「回収実績なし」)を組み合わせて表示する。回収効率が高いラベルから並び、同値は label 名昇順。
- **カバレッジ推移**: 各反復のユニットテストカバレッジ(%)の時系列推移。
- **累計コスト**: 各反復にかかった Builder/Adversary/Ideation 合計費用(USD)の推移。
- **承認率推移**: Adversary レビューが承認 (approved) した割合(%)の推移。
- **マージ率推移**: 反復した PR が実際にマージされた割合(%)の推移。
- **E2E失敗率推移**: verify に到達した反復のうち `npm run test:e2e` が失敗した割合(%)の累積推移。failed（クラッシュ）反復は verify に到達しておらず未測定のため含めない。
- **変更行数推移**: 各反復でコミットされた diff の変更行数(changedLines)の時系列推移。failed（クラッシュ）反復はコミット前に終了しており未測定のため含めない。
- **Builder改善の前反復比較**: 直近2件の測定済み(verify到達済み)反復について、revise回数・変更行数・カバレッジ・builderコストを前反復と比較し、各指標が改善/悪化/変化なしのいずれかを表示する。測定済み反復が2件未満の場合は「データなし」を表示する。
- **モデルコストの内訳**: 全反復の累計コストを Builder/Adversary/Ideation の役割別、および実際に使われたモデル名別に集計した内訳。failed（クラッシュ）反復も実際に費用が発生しているため含める。
- **Cost効率（USD per 承認PR）**: 全反復の累計コストを「承認PR」（adversary が approve し、かつ実際に PR が開かれた反復）の件数で割った実効コスト。失敗・見送り反復のコストも分子に含めることで、単純なマージ済みPRのコストより実態に近い効率を示す。承認PRが1件も無い場合は「データなし」。
- **Ideation提案品質低下の多面的早期検知**: 提案ドロップの連続・着手リードタイムの悪化傾向・早期abandonment（着手直後にreviseなしで見送られる）の悪化傾向・提案規模とドロップ率の相関、という性質の異なる4つの面（既存の各分析を束ねたもの）のうち、同時に何面が悪化を示しているかで警戒レベル（平常/注視/警戒）を判定する。単一指標のブレをノイズとして無視しつつ、複数の面が同時に悪化していればideation自体の生成品質が落ちている前兆として早期に検知する。各面は算出に必要なデータが揃っていない場合「データ不足」として悪化判定の対象から除く。ideation が1件も提案を行っていない場合は「データなし」。
- **Ideation提案消費成功率の信頼度トレンド**: 「信頼度加重スコア（少数サンプルの暴れ対策）」が builder モデル別のマージ率にベイズ縮約をかけるのと同じ考え方（信頼度 = count / (count + 事前重み5)）を、対象を ideation の提案（nextIssues）が実際に着手されmergedに至ったかという提案消費成功率に差し替えて適用する。ideation が提案したissueのうち実際に着手された順に累積success件数/総件数を積み上げ、生の成功率をどれだけ信用してよいかを示す信頼度と、全体平均側にベイズ平均で縮約した重み付き成功率を折れ線で推移表示する。サンプルが積み上がるほど信頼度は1に近づく。他のIdeationパネルが着手率・リードタイム・コスト効率という別の切り口を見るのに対し、こちらは「少数サンプルの結果をどこまで信用できるか」を可視化する点が異なる。着手済みissueが1件も無い場合は「データなし」。
- **Ideation 失敗率**: バックログ補充のために ideation が実際に実行された反復（cost.ideationUsd > 0）のうち、次の issue を1件も生成できなかった割合。ready が既に足りていて ideation 自体がスキップされた反復は分母に含めない。ideation が1件も実行されていない場合は「データなし」。
- **Ideationコスト効率と生成品質の関連性**: ideation が提案した issue 1件あたりのコスト単価（cost.ideationUsd ÷ 提案件数）と、その提案 issue が実際に後続反復として着手されたときの承認率・マージ率の Pearson 相関係数。反復ごとの単価・着手件数・承認率・マージ率も一覧表示する。着手前の提案（まだ後続反復が無い）は「未着手」と表示し、相関算出の母集団から除く。ideation が1件も提案を行っていない場合は「データなし」。
- **Ideation提案と実消費の対応関係**: ideation が提案した issue 1件ごとに、提案時点のコスト単価（cost.ideationUsd ÷ 提案件数）と、実際に着手された反復が消費した総コスト（着手反復の cost.totalUsd）・結果（verdict）を1行ずつ対応付けて一覧表示する。「Ideationコスト効率と生成品質の関連性」が反復(batch)単位で単価と承認率/マージ率の相関を見るのに対し、こちらは issue 単位で「見積り」と「実績」を直接突き合わせる。未着手の提案issueは「未着手」と表示し、実消費コスト合計・倍率（実消費 ÷ 提案時点コスト）の集計対象から除く。ideation が1件も提案を行っていない場合は「データなし」。
- **Ideation→着手までのリードタイム・着手成功率観測**: ideation が提案した(nextIssuesに含めた)ユニークissueのうち、実際に別反復として着手（issue.numberとして受理）された割合を着手成功率として表示し、まだ着手されていない issue 番号もあわせて一覧化する。着手済みissueについては、提案時点（提案元反復のfinishedAt）から着手時点（着手反復のstartedAt）までのリードタイム(分)を折れ線で示し、直近3件と直前3件の平均を比較して「悪化傾向」「改善傾向」「横ばい」を判定する（変化率が±5%未満は横ばい扱い）。「Issue生成からIssueクローズまでの解決時間トレンド」がゲート結果まで含めた解決全体を見るのに対し、こちらはゲート結果を含まず「バックログに積まれてからビルダーが手を付けるまで」だけを切り出す。ideation が1件も提案を行っていない場合は「データなし」。
- **バックログ枯渇予測（low_water 到達 ETA）**: data/runs には実際の ready 件数が記録されないため、orchestrator の ideation_low_water 既定値(6)を起点に、各反復の正味増減（nextIssues件数 − 消費1件）を積算した相対残量で近似する。直近5反復の平均増減を消費速度とし、負（純減）であれば低水位に到達するまでの反復数を推定する。既に基準線以下なら「低水位に到達済み」、減少していなければ「減少傾向なし」と表示する。
- **反復ごとのバックログ増減フロー**: 「バックログ枯渇予測」が直近window分の集計値（速度・ETA）だけを見るのに対し、こちらは全反復それぞれの生成件数（inflow）・消費1件（outflow）・その差分（net）をゼロ線を挟んだ増減バーとして時系列表示する。上に伸びる緑バーは純増、下に伸びる赤バーは純減の反復を示し、生成合計・消費合計・純増減合計・最新の相対残量もあわせて表示する。
- **バックログ生成レート監視**: 「反復ごとのバックログ増減フロー」「バックログ枯渇予測」が相対残量（積算値）を見るのに対し、こちらは生成数（nextIssues件数）そのものの推移だけを監視する。1反復は必ず1件消費するため、直近5反復の平均生成数が1件/反復を下回ると先細り方向。生成不足（0件）の反復が3回連続すると発報し、直近5反復・全反復それぞれの平均生成数と、生成不足の連続反復数を表示する。
- **Ideation実行と消費のタイミングのズレ検知**: 他のIdeationパネルがissue単位のリードタイムを見るのに対し、こちらはideationが実際に提案した反復どうしの間隔（実行間隔）と、その提案issueが着手された反復どうしの間隔（着手間隔）という2つの独立したイベント発生リズムを比較する。着手間隔÷実行間隔の比率が2倍以上開くと「実行が先行（バックログ増加方向）」または「消費が先行（在庫枯渇方向）」として発報する。実行・着手のいずれかが2件未満の場合は判定不可と表示する。
- **ゲート不通過理由の分類**: 全反復の gateReasons（ゲートを通過しなかった理由）を「verify失敗」「e2e失敗」「adversary未承認」「adversary出力解析不能」「変更行数超過」「保護パス変更」「変更なし」「例外クラッシュ」「その他」に分類し、出現件数の多い順に一覧表示したもの。変更行数超過や例外メッセージのように具体的な数値・文言が反復ごとに異なる理由も、共通のパターンで同じ分類にまとめる。「adversary未承認」は gateReasons 文字列だけでは区別できない2種類（具体的な欠陥を指摘した棄却／adversaryの応答を構造化できず安全側に倒した技術的棄却）を含むため、後者は run.adversary.summary を手がかりに「adversary出力解析不能」として分離する。
- **ゲート理由の時系列burden**: gateReasons を持つ反復ごとにカテゴリ別の出現件数を積み上げ棒グラフで表示し、いつ・どのカテゴリの負担が重かったかを時系列で見えるようにしたもの。
- **ゲート失敗別 reviseの実質コスト**: 他のゲート系パネルが出現件数（頻度）だけを見るのに対し、こちらはカテゴリごとに実際にかかったコスト(USD)・所要時間・revise回数を合算し、合計コストの多い順に一覧表示したもの。同じ出現件数でも、revise を繰り返してようやく解消するカテゴリと revise 前に即座に abandon するカテゴリとではループが払う実質コストの実態が異なるため、revise 1回あたりのUSD/所要時間も併記する。該当カテゴリの全反復が revise 0回（即abandon等）の場合は0除算を避けてその旨を表示する。gateReasonsを持つ反復が1件も無い場合は「データなし」。
- **ゲート理由の深刻度スペクトラム（復旧コスト分析）**: 「ゲート失敗別 reviseの実質コスト」がverdictを区別せずカテゴリ単位でコストを合算するのに対し、こちらはカテゴリ×verdict（failed=クラッシュ/abandoned=自動見送り/needs-human=旧経路の人間対応）の2軸でコスト・revise回数を分け、GateFailureTypesPanelが採用する深刻度順（クラッシュ→自動見送り→旧経路）の重みで加重平均した「深刻度スコア」（1〜3）を算出する。同じカテゴリでも自動で見送れた場合と、クラッシュや人間対応にまでエスカレーションした場合とでは復旧コストの実態が大きく異なるため、カテゴリを深刻度スコア降順に並べたスペクトラム上に可視化し、各カテゴリの下にverdict別の反復数・平均コスト・revise平均回数を表示する。failed/abandoned/needs-humanのいずれでもgateReasonsを持つ反復が1件も無い場合は「データなし」。
- **ゲート不通過理由のカテゴリ別トレンド**: gateReasons のカテゴリ別出現件数を直近3反復と直前3反復のローリング窓で比較し、「悪化」「改善」「横ばい」を判定したもの。閾値（0.5件/反復）未満のブレは横ばい扱いとし、悪化・改善しているカテゴリだけを変化幅の大きい順に一覧表示する。比較対象の反復が不足している場合は判定不能である旨を表示する。
- **ゲート不通過理由の連鎖（パス別）**: 他のゲート系パネルが全反復・全カテゴリを1つの分布/時系列に集約するのに対し、こちらは gateReasons を持つ反復（パス）ごとに、その回でどのカテゴリがどの順で連鎖して発生したか（例: e2e失敗 → adversary未承認 → 変更行数超過）をそのまま新しい順に一覧表示する。adversaryの応答が構造化できず技術的に棄却された反復は「adversary出力解析不能」として区別され、「adversary未承認」（内容を読んで却下）と混同されない。gateReasonsを持つ反復が1件も無い場合は「データなし」。
- **ゲート理由の時系列カオス分析（連続非通過の根本原因パターン）**: gateReasons を持つ反復が iteration 番号で途切れずに2回以上連続した区間（streak）ごとに、各反復の根本原因カテゴリ（gateReasons の先頭理由）が区間内でどれだけ入れ替わったかを「固定」（毎回同じ原因が居座っている＝reviseが根本原因を直せていない兆候）「混在」「カオス」（毎回原因が変わる＝ゲート自体が不安定/多面的な兆候）の3段階で判定する。gateReasonChainPanel が1パスごとの理由の連鎖を見せるのに対し、こちらは複数パスにまたがる連続失敗の「パターンの安定度」を見る。merged/paused/dry-run等でgateReasonsが空になった反復や、iteration番号が飛んだ箇所はそこでstreakを区切る。2回以上連続する区間が1つも無い場合は「データなし」。
- **ゲート連続失敗の理由単一化パターン認識**: 上記カオス分析の streak（連続非通過区間）を、さらに「終盤に根本原因が一つへ絞られたか」で分類する。chaosLevel は streak全体の入れ替わり回数を1つの指標に集約するため、「mixed判定だが実は終盤は単一原因に落ち着いてきた（絞り込みが効き始めた）」streakと「最後まで入れ替わり続けた」streakを区別できない。こちらは streak の末尾から見て同じ根本原因が何反復連続しているかだけを見て、「最初から単一原因」（最初から最後まで同じ）「単一原因に収束」（途中までは入れ替わったが末尾2反復以上は同じ原因で終わった）「収束せず」（最後の反復の原因が直前と異なる）の3水準で判定し、収束した場合は収束開始反復と持続反復数もあわせて表示する。streakが1つも無い場合は「データなし」。
- **ゲート不通過理由×モデル別 Adversary承認率**: 「ゲート不通過理由の分類」がカテゴリの出現件数だけを集計するのに対し、こちらはそのカテゴリの反復をレビューした adversary モデル別に分割し、各(カテゴリ, モデル)の組み合わせで adversary が実際に approve していた割合(%)を表示する。「adversary未承認」「adversary出力解析不能」は分類の定義上 adversary.approved が常に false のため承認率は常に0%になる（バグではない）。一方 verify失敗・e2e失敗等は adversary の判断とは独立した失敗要因なので、「approveしたのにverify/e2eで落ちた」というモデルごとの見落とし傾向が見える。gateReasonsを持つ反復が1件も無い場合は「データなし」。
- **Abandoned反復の追跡・分析**: `abandoned`（ゲートを再試行しても満たせず、人間に振らず自動で見送った）反復だけを他の非マージ類型（failed/needs-human/paused/dry-run）と混ぜずに集計したもの。累積見送り率・浪費コスト(USD)・平均revise回数・最多のゲート不通過理由カテゴリをサマリー表示し、各abandoned反復を新しい順に issue番号・タイトル・gateReasons込みで一覧表示する。abandoned が1件も無い場合は「データなし」。
- **打ち止め（abandoned）の原因分類**: 「Abandoned反復の追跡・分析」のサマリーが最多カテゴリ1件しか見せないのに対し、こちらは「ゲート不通過理由の分類」と同じ表現（カテゴリ別の件数・割合バー・対象iteration）を abandoned 反復だけに絞り込んで適用し、原因カテゴリがどう分布しているか（例: adversary未承認が過半数を占めるのか、複数原因に分散しているのか）を一覧できるようにする。failed/needs-human等、他の非マージ類型のgateReasonsは集計に混ぜない。さらに各カテゴリの行には、そのカテゴリが abandoned 内で占める割合を、gateReasons を持つ全反復（abandoned含む母集団）での占有率と比較したバッジ（全体より突出/全体より少ない/全体と同程度、差分pt付き）を表示し、差が±10ptを超えて最も突出しているカテゴリがあれば見出し直下にサマリー文で示す。abandonedの内訳を単体で見るだけでは分からない「他の非マージ類型と比べてこの反復群特有の原因なのか、gateがそもそも全体的に苦手としている原因なのか」を切り分けるためのもの。abandoned が1件も無い場合は「データなし」。
- **Adversary承認済みなのにBuilder実装失敗**: 「Adversary 承認⇔実結果 乖離」の falseApprove が verdict の一致/不一致だけで非マージ全般を一括りにするのに対し、こちらは adversary.approved=true かつ verdict!==merged の反復の gateReasons を classifyGateReason で分類し、adversaryNotApproved/adversaryUnparseable（adversary自身の判断内容の分類で、承認済み反復には定義上現れない）を除いた「builder側の要因」（verify失敗・e2e失敗・変更行数超過・保護パス変更・変更なし・例外クラッシュ等）を持つ反復だけに絞り込む。「承認したのにレビューの中身が実装の成否を保証していない」というレビュー品質の異常兆候を検知率(%)・浪費コスト(USD)・最多の原因カテゴリでサマリー表示し、該当反復を新しい順に issue番号・タイトル・verdict・原因カテゴリ・gateReasons込みで一覧表示する。paused/dry-runのようにゲート自体は通過している（gateReasonsが空）反復は対象外。該当反復が1件も無い場合は「データなし」。
- **Paused/Dryrun反復の停止理由・生存時間分析**: `paused`（人間がキルスイッチで停止）と`dry-run`（最初からマージしない設定）はどちらもゲート自体は通過済みで gateReasons が空のため、abandonedのようにゲート不通過理由では分類できない。代わりに停止理由（paused/dry-run）別に件数・PR開設件数・合計コストを集計し、「生存時間」として各反復の完了後runs全体の最新反復まで何反復が経過したか（survivalIterations）の平均・最大を表示する。経過時刻ではなく反復数で測るのは、ビルド時点で決定的に計算するため。最も長く放置されている反復と、各反復の詳細も新しい順に一覧表示する。該当反復が1件も無い場合は「データなし」。
- **Gate通過後Pauseパターン分類・離脱検知**: 「Paused/Dryrun反復の停止理由・生存時間分析」がpaused/dry-runをまとめて停止理由と生存時間だけを見るのに対し、こちらは`paused`（ゲート通過後キルスイッチでマージ直前に止まった）反復単体を、停止のされ方（revise無しで承認され即停止したclean-pause／revise後に承認されて停止したcontested-pause）と、その後の状態の2軸で分類する。後者は「離脱検知」が主眼で、同じissueが後続反復で再実行されていれば、その一時停止は実質的に見捨てられやり直されたと判定して`reattempted`、再実行が無くsurvivalIterationsが3反復以上経過していれば「放置され続けている」離脱リスクとして`stalled`、それ未満ならまだ判断がつかない`pending`とする。最も離脱リスクが高い(stalledかつ最長放置)反復と、各paused反復の詳細も新しい順に一覧表示する。paused が1件も無い場合は「データなし」。
- **ドライラン・一時停止の再開成功率トレンド**: 「Gate通過後Pauseパターン分類・離脱検知」の`reattempted`判定（同じissueが後続反復で再実行されたか）をpaused/dry-run両方に拡張し、再実行後の実際の結末（最終的にmergedへ至ったか＝再開成功）まで踏み込む。再開された反復だけに絞り込んだ累積再開成功率(%)の推移を折れ線で示す。まだ再開されていない反復を分母に含めると「再開すらされていない」ことと「再開したが失敗した」ことが区別できず率が見かけ上低く出てしまうため、再開された反復のみを対象にする。paused/dry-runが1件も無い場合は「データなし」、1件も再開されていない場合は件数のみ表示する。
- **revise 回数の分布**: 各反復の revise 回数を棒グラフで示し、中央値（実線）と外れ値の閾値（破線）を重ねたもの。閾値を超えるバーは赤色で強調される。
- **Model別 revise回数の分布**: verify に到達した反復を Builder に使われたモデル別にグルーピングし、平均・中央値・最小〜最大・件数を一覧表示したもの。平均revise回数が多いモデルほど上に表示され、どのモデルが revise を重ねやすいかを比較できる。
- **Verdict別 revise回数の分布**: 全反復を判定 (verdict) 別にグルーピングし、平均・中央値・最小〜最大・件数を一覧表示したもの。Model別の分布とは異なり failed（クラッシュ）反復も「クラッシュするまでのrevise回数」として独立したグループに含め、merged 等と並べて比較できるようにする。平均revise回数が多いverdictほど上に表示される。
- **revise回数とverdictの関連図**: revise回数を0/1/2/3回以上の4区分に分け、各区分内で反復がどの判定(verdict)に分岐したかを積み上げ帯グラフで示したもの。「Verdict別 revise回数の分布」が平均・中央値に集約するのに対し、こちらは「revise 0回はほぼ全部mergedだが、3回以上になるとabandonedの割合が増える」といった閾値付近の分岐傾向をそのまま見せる。各区分の帯の右上にmerged到達率(%)も表示する。
- **Reviseサイクル別 APIコスト分布と回収効率**: revise回数を0/1/2/3回以上の4区分に分け、区分ごとに各反復のAPI呼び出しコスト(cost.totalUsd)の平均・中央値・p90・最小〜最大を表示する。「revise回数とverdictの関連図」が件数の分布を見るのに対し、こちらは同じ4区分をコスト（金額）の分布として見る。あわせて区分内でmergeに到達した割合を「回収」として示し、merge到達1件あたりの実効コストも併記することで、revise回数が増えるほどコストが嵩む一方でその支出がmergeとして回収できているかを比較できる。costEfficiencyと同様、failed/abandonedのコストも「回収できなかった支出」として分子に含める。
- **Verdict別 平均CI/ゲート通過時間の比較**: 全反復を判定 (verdict) 別にグルーピングし、所要時間(durationSec)の平均・中央値・最小〜最大・件数を分単位で一覧表示したもの。「CI/ゲート通過時間のトレンド観測」が全反復を通した時系列の悪化/改善しか見せないのに対し、こちらは「どの verdict に落ち着いた反復が時間を要しているか」を比較できる。Verdict別 revise回数の分布と同様、failed（クラッシュ）反復も「クラッシュするまでの経過時間」として独立したグループに含める。平均所要時間が長いverdictほど上に表示される。
- **Verdict別 マージまでの経路長**: merged 以外の verdict で終わった反復ごとに、次に merged が現れる反復まで何反復かかったか（経路長）を、その反復自身の verdict別にグルーピングして平均・中央値・最小〜最大・件数で表示する。「Verdict別 revise回数の分布」「Verdict別 平均CI/ゲート通過時間の比較」がその反復自身の実測値を比較するのに対し、こちらは「そこから何反復先で merge に辿り着くか」という前方参照の指標。このデータの範囲内で後続に merged が一度も現れない反復（末尾で結末が付いていない）は経路長を計算できないため対象から除く。平均経路長が長い（mergeから遠い）verdictほど上に表示され、経路長を計算できた反復が1件も無い場合は「データなし」。
- **Verdict遷移の自動分類・離脱パターン検知**: 隣接する2反復間のverdict遷移を「連続成功」「回復」「同型で足踏み」「不通過の型が変化」「悪化」の5種に自動分類し、種別ごとの件数・割合を帯グラフで示す。あわせて非マージ verdict が2回以上連続した区間を「離脱パターン」として抽出し、各区間がmergedで途切れて回復したか(recovered)、データ終端までabandonedで終わり離脱したか(droppedOut)、まだ結末の付いていない進行中か(ongoing)を判定して、区間内のverdict推移・浪費コストとともに一覧表示する。比較対象となる隣接反復が無い場合は「データなし」。
- **Verdict遷移の根本原因パターン化**: 「Verdict遷移の自動分類・離脱パターン検知」が遷移を種別だけで分類するのに対し、こちらは各遷移に伴うgateReasons[0]（最初にブロックした条件）を根本原因カテゴリとして紐付け、「種別×根本原因」のクロス集計で表示する。regressed/repeatedFailure/shiftedFailureは遷移先の反復が今回何を原因にブロックされたかを、recoveredは遷移元の反復が何を乗り越えて回復したかを採用する。これにより「同型で足踏み」が verify失敗による足踏みなのか adversary未承認による足踏みなのかを区別できる。sustainedSuccessや、paused/dry-runのようにgateReasonsが常に空の反復が関わる遷移は根本原因を特定できないため集計から除く。根本原因を特定できる遷移が1件も無い場合は「データなし」。
- **E2E失敗とコード変更範囲(diff size)の相関**: verify に到達した反復を e2e成功/失敗の2群に分け、それぞれの平均変更行数(changedLines)と、e2e成功/失敗(0/1)と変更行数の Pearson 相関係数を表示したもの。失敗群の平均が成功群よりどれだけ大きい/小さいかを文章でも示し、diffが大きい反復ほどe2eが失敗しやすい傾向があるかを見る。e2e結果が全反復で同じ（分散0）の場合は相関係数を「算出不可」とする。e2e失敗した反復の番号も一覧表示する。verify に到達した反復が1件も無い場合は「データなし」。
- **E2E失敗相関のBuilder稼働量分離（偏相関分析）**: 「E2E失敗とコード変更範囲(diff size)の相関」が示すdiff sizeとe2e失敗の関係が、Builder稼働量(cost.builderUsd)という別軸に引きずられた見かけ上の相関ではないかを、偏相関係数（もう一方の変数を統計的に固定した相関）で切り分ける。diff sizeとBuilder稼働量それぞれの単純相関、両者間の相関に加え、双方向の偏相関（diff size|稼働量固定、稼働量|diff size固定）を表示し、diff size側の偏相関が単純相関の50%未満に縮んだ場合は「交絡の疑いが強い」、縮まなければ「独立に関係している」と判定する。diffSizeとBuilder稼働量が完全に連動している（相関が±1）場合は偏相関の分母が0になり「算出不可」（判定不能）となる。verify に到達した反復が1件も無い場合は「データなし」。
- **Builder生成量と承認率のカップリング分析**: 「E2E失敗とコード変更範囲(diff size)の相関」が changedLines と2値結果(e2e成功/失敗)の相関を反復横断で1つの係数に集約するのに対し、こちらは直近3反復と直前3反復のローリング窓で、Builderの生成量(changedLinesの平均)とAdversary承認率の変化がそれぞれどちらの方向に動いているかを比較する。生成量の変化率(%)と承認率の変化幅(pt)が同方向なら「連動」、逆方向なら「逆連動」、どちらかの変化が小さすぎれば「横ばい」と判定する。あわせてverify到達反復全体でのchangedLinesとadversary.approved(0/1)のPearson相関係数も表示する。比較対象となる直前ウィンドウが取れない（verify到達反復が1件以下）場合は「データなし」。
- **モデル選択の効果測定**: Builder に使われたモデル（例: Sonnet vs Haiku）別に、マージ率・承認率・e2e失敗率・平均revise回数・平均カバレッジ・平均コストをまとめて比較したもの。revise回数のみを見る「Model別 revise回数の分布」とは異なり、実際にマージまで到達した効果とコストを合わせて見ることで、どのモデルを選ぶべきかの判断材料にする。マージ率の高いモデルほど上に表示される。
- **信頼度加重スコア（少数サンプルの暴れ対策）**: 「モデル選択の効果測定」の生マージ率は、反復数が少ないモデルほど1件の結果で大きく振れる（例: 1件しかない新モデルが merged 1件で「マージ率100%」と表示され、実績十分な既存モデルより優れて見えてしまう）。この問題を緩和するため、件数が少ないモデルほど全体平均側にベイズ的に縮約した「加重スコア」を算出して表示する。生マージ率・件数・信頼度（0〜100%、件数が多いほど高くなり生の値を信用してよいことを示す）も併記し、件数が一定未満のモデルには「少数サンプル注意」バッジを付ける。加重スコアの高いモデルほど上に表示される。
- **Model効率分析（コスト×成功率の役割別分解）**: 「モデル選択の効果測定」が Builder モデルだけを対象にするのに対し、こちらは Builder/Adversary/Ideation の役割別に、その役割で使われたモデルごとのマージ率と、その役割が実際に消費したコスト(USD)を分解して表示する。「モデルコストの内訳」は役割をまたいで同じモデルのコストを合算するが、こちらは役割単体のコストのみを集計するため、同じモデルが複数の役割で使われていても混ざらない。マージ1件あたりの実効コストも併記し、マージ0件のモデルは0除算を避けて「算出不可」と表示する。役割ごとにマージ率の高いモデルから並ぶ。
- **モデル別 承認率・マージ率比較**: Builder に使われたモデル別に、承認率とマージ率を同じスケールの横棒で並べて直接比較したもの。「モデル選択の効果測定」がマージ率降順で並ぶのに対し、こちらはモデル名の昇順で固定し、承認率とマージ率の差分（承認→マージのギャップ）を表示することで、承認はされたのにマージまで到達していないモデル（paused/dry-run 等で止まっている）を見つけやすくする。
- **Adversary 承認⇔実結果 乖離**: 「モデル別 承認率・マージ率比較」が builder モデル別に承認率とマージ率という2本の集計値のギャップ(pt)を見せるのに対し、こちらは adversary モデル別に「個々の反復で承認判断(adversary.approved)と実結果(verdict)が一致していたか」を件数ベースで突き合わせる。承認した(approved=true)のに実際は merged にならなかった反復を「見落とし」として件数・率・発生した反復番号つきで表示し、対称に却下したのにmergedになった「誤却下」も算出する。両者の合計が全判定件数に占める割合を「乖離率」として adversary モデルを乖離率の高い順に並べ、承認を出しても実際の結果を伴わない傾向が強いモデルを見つけやすくする。failed（レビュー未到達）反復は判定対象から除く。verify に到達した反復が1件も無い場合は「データなし」。
- **Adversaryモデル別×Verdict別 見落とし率マトリクス**: 「Adversary 承認⇔実結果 乖離」が adversary モデル別に見落とし件数を verdict の種類を問わず1本の集計値へ合算するのに対し、こちらはモデル×verdict(abandoned/needs-human/paused/dry-run)のクロス集計として見落とし率を分解し、どのモデルの、どの verdict 種別で見落としが集中しているかを表示する。行は見落とし率（非マージ反復に占める見落とし件数の割合）が高いモデル順に並び、非マージ反復が1件も無いモデルは「非マージ反復なし」と表示する。failed（レビュー未到達）反復は判定対象から除く。verify に到達した反復が1件も無い場合は「データなし」。
- **Builderモデル切り替えのA/B比較**: 「モデル選択の効果測定」「モデル別 承認率・マージ率比較」が期間全体でモデルごとに全反復を合算するのに対し、こちらは Builder に使われたモデルが iteration 順で実際に切り替わったタイミングだけを取り出し、切り替え直前の連続区間(A)と直後の連続区間(B)で承認率・マージ率を直接A/B比較する。同じモデルが後で再登板しても過去の区間とは合算せず、切り替えイベントごとに改善/悪化/変化なしを判定する。切り替えが一度も無い（builder が同一モデルのまま）場合は「データなし」を表示する。
- **Model別 承認率トレンド観測**: Builder に使われたモデル別に、累積承認率(%)の推移を折れ線で並べて表示したもの。「モデル選択の効果測定」「モデル別 承認率・マージ率比較」が期間全体を1点のサマリーに集約するのに対し、こちらはモデルごとに独立した時系列で承認率を追い、モデルを切り替えた後に承認率が実際に改善/悪化しているかを比較できるようにする。verify に到達した反復が無いモデルは「データなし」と表示される。
- **Model ペア相性の乖離検知**: 「モデル選択の効果測定」「Adversary 承認⇔実結果 乖離」がモデルを builder/adversary それぞれ単独の軸で評価するのに対し、こちらは builder × adversary の「組み合わせ」単位で、実測マージ率が両モデルの単体成績から期待される水準（二元配置の加法モデル: builder単体マージ率 + adversary単体マージ率 - 全体平均マージ率）からどれだけ乖離しているかを検知する。期待値との差(pt)が大きい組み合わせほど、その2モデルの相性が良い方にも悪い方にも通常の想定から外れていることを示す。件数が一定未満、または builder が常に同じ adversary としか組んだことが無い（単体成績とペア実績が交絡し乖離が定義上0になる）組み合わせは乖離判定の対象外とし、その旨を表示する。反復が1件も無い場合は「データなし」。
- **直近の反復**: 直近 20 件の反復を新しい順に並べ、判定 (verdict)・revise 回数・コストを一覧表示したもの。
- **ループが生成した改善バックログ**: 各反復の完了時にループが自動生成した次の issue 候補の一覧。
